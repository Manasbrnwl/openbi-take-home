## Run it (≈ 5 minutes)

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/) (or plain `pip`).

```bash
uv venv .venv --python 3.12
uv pip install --python .venv -r requirements.txt      # or: pip install -r requirements.txt

.venv/Scripts/python -m pipeline.run                    # macOS/Linux: .venv/bin/python
.venv/Scripts/python -m pytest -q                       # controls, idempotency, access control

NB_ENV=dev .venv/Scripts/python -m uvicorn app.main:app --reload
# open http://localhost:8000  — dev password for every user: northbeam-demo
```

## Design in five points

1. **Bronze is as-landed.** Every value is stored as text, with `_source_file`, `_source_row`,
   `_file_sha256`, `_batch_id` and `_loaded_at`. A file whose hash was already loaded is skipped,
   so a re-run adds nothing (tested). Silver and Gold are deterministic full rebuilds from the
   latest batch, inside one transaction.
2. **Stage is history.** `gold.fact_stage_history` holds one row per period in a stage
   (`valid_from`, `valid_to`). Any "as at" question reads it. The source `current_stage` is
   stale for 96 applications, so it is kept only for audit. → [docs/MODEL.md](docs/MODEL.md)
3. **People are not records.** 601 records collapse to 560 people on normalised phone. Email is
   deliberately *not* an identity key: 24 shared emails belong to different people.
   `bridge_candidate_record` keeps every source id.
4. **Orphans are kept, not dropped.** 23 applications and 9 interviews can't be tied to a valid
   requisition or application. They point at `req_key = -1`, every metric excludes them, and
   only admins can see them.
5. **One metric layer.** Every metric lives in `metrics/definitions.py`. The API calls
   `metrics.compute(...)` and returns the dict unchanged, and the frontend prints it.
   `tests/test_metric_single_source.py` fails the build if metric arithmetic (median,
   date_diff, `*100`, `toFixed`, stage-interval logic…) appears in `app/` or `frontend/`.
   Changing how time-to-hire is defined means changing exactly one function.

## Access control

Scope is resolved server-side from the verified token's `sub` only. Role and requisitions are
looked up in Gold on each request and applied as a SQL `WHERE req_key IN (…)` inside every
metric and list query. A request can't widen its own scope through query parameters, headers or
the body, and an out-of-scope requisition returns 404, the same as a non-existent one.
**How we convinced ourselves it can't be bypassed:**
[docs/ACCESS_CONTROL.md](docs/ACCESS_CONTROL.md). That covers token forgery, `alg=none`,
parameter and header tampering, deliberate mutation of the app to prove the tests bite, and
cross-checks on the real warehouse.

## Deployment

Target: **Render free web service** via Docker (`Dockerfile`, `render.yaml`), at zero cost. The
image runs the pipeline at build time and bakes a read-only warehouse in. The app runs as a
non-root user. `NB_JWT_SECRET` is generated by Render, and `NB_DEMO_PASSWORD` is set in the
dashboard. The app refuses to start in prod without both.

Verified locally in prod mode (uvicorn + curl): login, scoped metrics, tamper attempts and 404s.
The Docker image itself was not built locally (Docker daemon unavailable on the build machine);
Render builds it from the Dockerfile.

**Before real users touch it, I would change:**
- **Identity:** replace the shared demo password with the client's IdP (Entra ID / OIDC), with
  MFA and short-lived tokens plus refresh, and with revocation (today a token stays valid until
  it expires, up to 60 minutes).
- **Data refresh:** baked-in data means a redeploy per refresh. Move to a scheduled pipeline
  writing to object storage, with the API reading the latest published snapshot.
- **PII:** encrypt at rest, mask phone and email unless the role needs them, keep an audit log
  of who viewed which candidate, and set a retention policy (DPDP Act 2023 for Indian
  candidates).
- **Ops:** structured request logs without PII, rate limiting on `/auth/login`, an uptime alert,
  and dependency pinning plus scanning in CI. The free tier also sleeps when idle, so the first
  request is slow.
- **SCD2 on requisitions:** if a requisition changes hiring manager, access should follow the
  current owner while history stays attributable.

## What I left out, and why

- **SCD Type 2 dimensions.** The extract is a single snapshot, so there is no attribute history
  to version yet. Bronze keeps every batch, so the inputs accumulate from load two onwards.
- **Incremental Silver/Gold.** At about 10k rows a full rebuild takes under a second, and
  incremental logic would add risk without benefit. Surrogate keys would need a persisted
  key-map first.
- **CRUD, visual design, and Power BI / Fabric semantic model.** Not scored. The metric layer is
  shaped so its definitions map one-to-one onto DAX measures.
- **Extension.** See [docs/ESTIMATES.md](docs/ESTIMATES.md) for whether time allowed one.
